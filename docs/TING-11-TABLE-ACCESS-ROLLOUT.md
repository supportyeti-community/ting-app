# TinG — TING-11 Table Access Context Rollout Runbook

**Scope:** PR #28 — bind anonymous guest ordering to a secured table access context.

**Status:** Repository-only rollout plan. This document does not authorize a production database migration or a merge to `main`.

## 1. Why this rollout exists

Before PR #28, a guest order was accepted when the caller supplied a valid public venue route and a regex-valid table number. Tenant ownership, item ownership, pricing, totals and order lifecycle were server-authoritative, but physical table possession was not proven.

PR #28 adds this invariant:

`request tenant route + table number + issued table capability -> order submission`

A venue slug and table number alone must no longer be sufficient to create an order.

## 2. What changes for venues

Existing menu links remain usable for browsing.

Existing ordering links containing only:

`?client=<slug>&table=<table>`

must fail closed for order submission after the migration is live.

Ordering-enabled QR codes and NFC tags must instead encode a link containing an issued capability:

`?client=<slug>&table=<table>&ctx=<issued-256-bit-token>`

The guest page moves the capability into session storage and removes it from the visible URL after first load.

## 3. Capability properties

- Generated by Postgres through an authenticated tenant-manager RPC.
- Bound to one canonical tenant and one table number.
- 256-bit random bearer token.
- Only SHA-256 token hashes are stored in `table_access_contexts`.
- The plaintext token is returned only when issued so it can be embedded in the physical QR/NFC link.
- A valid token for one table must not authorize another table.
- A valid token for one tenant must not authorize another tenant.
- Issuing a new token does not silently invalidate previously issued tokens for that table.

## 5. Deployment order

Do not deploy the application code before the database migration is ready. Do not activate secured ordering for physical tables until both database and guest/admin application code are available together.

Recommended sequence:

1. Record the exact approved PR #28 head SHA and green CI evidence.
2. Merge PR #28 only after explicit production approval.
3. Allow the normal application deployment to complete and verify the deployed commit.
4. Apply `20261015000000_ting11_table_access_context.sql` to the production Supabase project under a controlled release window.
5. Verify PostgREST exposes the new `submit_order(..., p_table_token)` and `issue_table_access_context(...)` RPC contracts.
6. Sign in to the venue admin route as an authorized owner/admin.
7. For each ordering-enabled table, use the TinG QR generator to issue a secured table context.
8. Save the generated QR asset and program the same secured URL onto that table's NFC tag if NFC is used.
9. Mark the physical table/tag as provisioned in the rollout ledger before moving to the next table.
10. Run the live smoke test below for every provisioned table.
11. Only after every intended table is certified should the venue be considered ordering-ready.

## 6. Per-table rollout ledger

Maintain a temporary deployment ledger outside the public guest UI containing at least:

- venue/client slug
- table number
- QR generated: yes/no
- NFC programmed: yes/no/not used
- QR scan tested: yes/no
- NFC tap tested: yes/no/not used
- correct table shown: yes/no
- order submission tested: yes/no
- staff dashboard received correct table/order: yes/no
- operator/date

Do **not** record plaintext table capabilities in the ledger.

## 7. Live smoke test for each table

For each provisioned physical table:

1. Scan the generated QR from a fresh browser session.
2. Confirm the menu loads for the correct venue.
3. Confirm the correct table number is shown.
4. Confirm the browser address bar no longer retains the `ctx` capability after initial load.
5. Add an available item to the cart.
6. Submit one controlled test order.
7. Confirm the restaurant dashboard receives the order on the correct table.
8. Confirm authoritative server pricing matches the current menu price.
9. Advance the test order through the permitted lifecycle or clean it up using the normal operational process.
10. If NFC is used, repeat the same flow by tapping the programmed NFC tag.

## 8. Negative certification after production migration

Run these controlled checks before declaring the rollout complete:

- Open a historical URL containing only `client + table`; menu browsing may work, but order submission must fail closed.
- Change the table number in a valid secured URL while keeping the same capability; order submission must fail.
- Change the client slug while keeping the same table/capability; order submission must fail.
- An authenticated manager must not be able to issue a table context while routed to a tenant they do not manage.

Do not brute-force tokens or run load tests against production.

## 9. Failure handling

### If application deployment fails before the database migration

Do not apply the production migration. Restore the prior successful application deployment if necessary. No table reprogramming should have started.

### If the database migration fails

Stop the rollout immediately. Do not generate or program physical table links. Preserve the failure evidence and use the migration rollback/repair path reviewed for Supabase before retrying.

### If the migration succeeds but application behaviour is wrong

Stop table provisioning. Do not issue further table contexts. Because the release is deliberately fail-closed, prefer disabling new ordering rollout over reopening the old unauthenticated table trust path.

### If a specific QR/NFC capability is exposed or printed incorrectly

Do not weaken `submit_order()`. Issue a replacement capability for that table and replace/reprogram the affected physical asset. A follow-up revocation capability should be added if selective invalidation is required before public launch.

## 10. Rollback principle

The security migration should not be rolled back merely to restore old public `client + table` ordering. That would deliberately reintroduce the confirmed trust gap.

If production must be stabilized before table provisioning is complete, the preferred safe state is:

- menu remains available,
- ordering remains fail-closed for unprovisioned tables,
- staff/admin functionality remains available,
- provisioning resumes only after the deployment issue is corrected.

## 11. D-Day acceptance criteria

PR #28 is operationally complete only when:

- every intended ordering table has a secured QR and/or NFC link,
- each physical asset has passed the per-table smoke test,
- at least one negative old-link test has confirmed fail-closed behaviour,
- staff dashboard routing has been verified for the provisioned tables,
- no plaintext table capability has been copied into logs, docs, screenshots or deployment ledgers,
- the exact deployed application commit and production migration version are recorded in the final handoff.

## 12. Current decision boundary

Passing repository CI proves the implementation and disposable-environment behaviour. It does **not** by itself authorize production deployment.

The remaining production decision is explicit approval to merge/deploy PR #28 and perform the physical QR/NFC provisioning sequence above.
