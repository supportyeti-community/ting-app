## Category contract — recommended
- Add `public.menu_categories(id uuid PK, tenant_id uuid NOT NULL, name text NOT NULL, sort_order integer NOT NULL DEFAULT 0, created_at timestamptz, updated_at timestamptz)`; unique `(tenant_id,id)`; unique per-tenant normalized category name using an index, with display labels preserved; nonempty length-limited names. Composite FK to `tenants`.
- Add nullable `menu_items.category_id uuid` with composite FK `(tenant_id,category_id) -> menu_categories(tenant_id,id)`. Nullable during rollout ONLY. Existing dishes remain visible under a deterministic **Uncategorised** grouping until assigned; never silently hide them. A per-tenant “Uncategorised” category can be created during an explicit data migration after tenant-by-tenant review, using stable UUIDs; do not infer ownership.
- Category display: `ORDER BY menu_categories.sort_order, lower(name), id`; within category `ORDER BY menu_items.sort_order, lower(name), id`. Duplicate order values must be deterministic; reorder uses an authenticated, tenant-constrained transaction with optimistic version or row locking.
- Deleting a category with dishes must fail (RESTRICT) or require an explicit atomic reassignment; never cascade-delete menu items. Item ID, tenant, price and order references stay stable. Category renames/reorders are not recipe changes.
- Don't co-opt `tags` as categories. Existing item edit / stock / pricing retains current contracts.

## Allergen vocabulary — Australian requirements
FSANZ required names include wheat; barley, oats and rye where gluten-containing; fish; **crustacean distinct from mollusc**; egg; milk; lupin; peanut; soy; sesame; **individual** almond, Brazil nut, cashew, hazelnut, macadamia, pecan, pine nut, pistachio, walnut; and added sulphites at the applicable threshold. An undifferentiated `tree_nuts`, `shellfish` or `gluten` flag alone is not adequate to represent those declarations. Support groups as UI preferences only, expanding to underlying explicit types. Coeliac handling must consider wheat, barley, rye, oats, gluten ingredient sources, sourcing and kitchen cross-contact; no implied “coeliac-safe” certification from absence of an ingredient.

Primary sources: https://www.foodstandards.gov.au/business/labelling/allergen-labelling and https://www.foodstandards.gov.au/consumer/foodallergies/food-allergen-portal/Allergy-information-for-the-food-service-industry . Final venue-specific policy should be reviewed with qualified food-safety operators.

## Structured assessment contract — recommended
- `public.menu_allergen_codes(code text primary key, label text, active boolean)`: controlled migration-seeded vocabulary, not user-supplied free text.
- `public.menu_item_allergen_assessments(tenant_id uuid, menu_item_id uuid, allergen_code text, state text CHECK state IN ('contains','may_contain','assessed_absent','unknown'), evidence_note text, updated_at timestamptz, PRIMARY KEY(tenant_id,menu_item_id,allergen_code))`; composite item FK ensures tenancy. Absence of a row means **unknown**, not assessed absent. New items default unverified, with all codes effectively unknown.
- `public.menu_item_allergen_reviews(tenant_id uuid, menu_item_id uuid, safety_version integer NOT NULL DEFAULT 1, verified_version integer NULL, verified_by uuid NULL, verified_at timestamptz NULL, review_note text NULL, recipe_context text NULL, preparation_context text NULL, updated_at timestamptz)`; composite item FK and unique item key. Database check binds the three verified fields as a consistent set and `verified_version = safety_version` when review is current. Reviewer must be derived from `auth.uid()` in a privileged, guarded operation; never accept a browser-supplied reviewer ID.
- `recipe_context` and `preparation_context` are safety-relevant and must not be visible in the public menu read. Expose a **minimal tenant-routed, security-invoker or explicitly reviewed guarded read interface** with only public statuses and reviewer state; not private kitchen notes, staff identity or full review history.
- Each changed recipe/ingredients/preparation, allergen assessment row, or relevant supplier/substitution declaration atomically increments `safety_version` and clears review fields. Changes to name/price/order/category/image/availability alone do **not** invalidate unless their content describes a recipe/ingredient/preparation change; conservative option is to invalidate on description changes until fields are separated. An UPDATE/DELETE of any allergen assessment must invoke invalidation in the database, not only in UI. Document menu item DELETE policy for referencing reviews; preserve historical orders.
- Verification must be a dedicated controlled **RPC**, not direct table UPDATE: inside one transaction lock the item/review row, assert authenticated owner/admin tenant membership (using server-side membership, not JWT `user_metadata`), check all required codes have an explicit assessment and the reviewed recipe/preparation data is current, then set reviewer = `auth.uid()`, timestamp = server `now()`, verified_version = safety_version. Restrict EXECUTE from PUBLIC by default; explicitly grant to the intended authenticated role and enforce membership inside. Do not give Floor any generic menu or allergen mutation privilege.
- In the migration, **REVOKE** authenticated/anon UPDATE/INSERT/DELETE on protected allergen tables and ensure RLS on each public table. A `SECURITY DEFINER` RPC, if unavoidable, must have fixed `search_path`, explicit tenant+role checks, row locks and no unrestricted PUBLIC EXECUTE. Explicit privilege review must verify that a direct PostgREST write cannot forge `verified_by`, `verified_at`, `verified_version` or bypass invalidation. Existing broad `menu_items` UPDATE must not be able to modify a future safety-version column.
- Use a monotonic version + lock to reject stale review submissions (`expected_safety_version`); concurrent edit+verify must serialize with item row locking. No automatic trust of imported metadata, tags, or machine extraction.

## Guest policy — proposed pending founder sign-off
For each selected allergy expand UI groups to the concrete code set. Classify a dish:
1. `contains`: **conflict**; never label suitable.
2. `may_contain`: **cross-contact warning**; never label suitable.
3. `unknown`, missing code, absent/stale review: **not assessed**; never label suitable.
4. Only explicitly `assessed_absent` for every selected code with current versioned review: **no declared conflict in venue's current assessment**, NOT a safety guarantee.

**Proposed safest launch default:** with an active allergy filter, show conflict/cross-contact/unknown rows under an appropriately separated warning state and disable ordinary add-to-cart for affected items; show clear **Ask staff about this dish** action. This exact hide/warn/block rule requires founder approval, particularly whether guests may request/override a blocked item following staff consultation. With no allergy selected, show dishes but never decorate unverified dishes as “allergen-free”. No “safe for coeliacs” claim. Staff enquiry remains accessible globally and per item. Fail closed on network or absent assessment response; do not silently fall back to free-form tags.

## Batch import compatibility (FS-01B)
A future batch endpoint accepts a parsed, validated draft (CSV/Excel -> map -> preview/correct -> validate -> save draft -> allergen review). Require tenant identity from authenticated server context, idempotency key bound to tenant + import payload digest, per-row client key, strict decimal AUD price, duplicate diagnosis, category lookup/creation in one transaction, explicit rejected rows and committed result. Never import `verified*` fields, inferred allergens or arbitrary SQL. Retry with same idempotency+digest returns the same saved IDs; key reused with different digest errors. Draft records all unverified. No PDF/photo extraction in FS-01A.

## Risk / test matrix (must be executed before certification)
- Tenant A cannot attach an A item to B category, read B private review notes, assess B allergens or verify B dish.
- `anon`, guest and Floor cannot edit allergen assessment, attest review, or change category/price. Floor's later 86 operation may ONLY mutate availability with audit and race checks.
- forged reviewer/version/timestamp via PostgREST or RPC arguments denied; missing header/unknown slug fails closed.
- an edit to `recipe_context`, `preparation_context`, any allergen row or ingredient/description field invalidates; cosmetic category reorder does not.
- review/edit simultaneous races and stale expected-version requests fail without false verification.
- partial batch failure is atomic; replay with same key is deduplicated; conflicting payload/key rejected.
- old uncategorised items remain visible; category-delete cannot cascade items; order snapshot/status and server pricing unchanged.
- guest selected multi-allergen expansion, unknown/missing/stale data, allergy warnings and staff inquiry tested independently in real preview.
- inspect views/RPC grants and run restricted-role negative tests, native migration/reconstruction, REST API, and Supabase security advisors in disposable infrastructure. Avoid false PASS from regex-only checks.
